1. 背景与目标

团队使用形如 deploy_config.yml 的部署配置文件（主机清单 hosts、服务模式 service_mode、集群清单 clusters、网络映射 networking）驱动自动化部署工具。这类文件目前散落在各服务器与本地，存在三个问题：

  1. 没有集中版本管理：谁改了什么、当前生产用的是哪个版本，无从查证；
  2. 无法追溯变更：集群、实例、变量的增删改没有 diff 记录与回滚手段；
  3. 与 Nginx 配置管理割裂：系统已具备成熟的"推送→结构化入库→内容管理→版本快照"能力，但只服务 Nginx 文本，无法覆盖 YAML 文件。

因此，将同一套"配置管理"范式扩展到 通用 YAML 文件：运维可在任意服务器用 curl 命令把 YAML 推送入库，系统校验、结构化、留版本，并在 Web 界面完成浏览、编辑、对比、回滚与导出。

期望的可观察结果：运维完成一次推送后，能在系统中看到该文件的结构化内容与完整原文、变更 diff、历史版本，并能一键重新导出与推送命令相同的原始文本；任何被采纳的改动都自动留下可回滚的版本快照。

2. 范围

2.1 最小完整旅程（P0）

选择归属行业→ 上传 / curl 推送 YAML→ 语法校验 + 结构预览（diff）→ 确认提交（apply）→ 结构化树 + 全文双视图浏览→ 编辑 / 版本对比 / 回滚 / 导出
  • 进入条件：登录用户处于某个行业工作台，行业下存在"配置文件"入口；或用户手持有 YAML 文件与推送 token。
  • 完成证据：文件出现在该行业配置列表中，结构化树可浏览、全文可查看/编辑，存在 ≥1 个版本快照，可导出与入库内容一致的原文。
  • 主要失败恢复路径：推送内容不合法 YAML 或发生校验错误时，preview 阶段即拦截并给出定位提示，不产生任何入库副作用；apply 失败时任务标记失败且不生成新版本，系统保留最近一次成功版本供回滚。

2.2 P1 支持（本次一并规划）

  • YAML 语法错误定位（行号 + 建议）；重复键检测；
  • 注释保真：独立注释行与行内注释在重新导出时回到原位置；
  • 全文编辑支持语法高亮与"跳转到树节点对应行"；
  • 版本对比：任意两版本全文 diff。

2.3 明确排除

  • 决策不绑定 deploy_config.yml 的固定 schema（hosts/clusters/networking 等字段校验、集群/实例业务化卡片均不在本期）。本期按通用 YAML管理，样例文件只是验证载体。
  • 决策敏感值（密码、私钥、云厂商密钥）不做脱敏/加密等特殊处理，与普通配置同等展示与存储。
  • YAML 的语义级校验（如引用的集群是否存在）、跨文件引用解析，本期不做。

3. 产品模型与核心流程

3.1 业务对象

对象职责关键属性
YAML 配置（YamlConfig）一个被管理的 YAML 文件实体，归属于某个行业所属行业、名称、描述、启用状态、完整原文 content_text、乐观版本号、最近操作时间
YAML 节点（YamlNode）配置树的最小结构单元，表达任意嵌套层级父节点、类型（映射/列表/标量/注释）、键路径、值、原始行号范围、排序
推送任务（PushTask）一次推送的 preview→apply 两阶段记录状态（pending/applied/failed）、上传原文、解析结果、diff 明细、错误信息
推送令牌（PushToken）允许在无界面环境下提交的一次性凭证用途（preview/apply）、哈希值、有效期、是否已用
版本快照（Version）apply 成功时刻的完整原文快照，供对比与回滚归属配置、生成时刻、完整文本、操作人

3.2 推送生命周期

    ▼
语法校验 ──失败──► 返回定位信息（行号/重复键），任务置 failed，不落库

4. 功能需求

FR-01 推送与导入（preview / apply）P0

目的与触发

运维在任意能访问系统的服务器上，用 curl 携带 YAML 内容与一次性 token，将该文件纳入系统管理。支持两种入口：界面内选择文件上传；命令行 curl -F file=@… 推送。

处理规则

  1. preview 接口接收文件与 preview token，先做语法校验（见 FR-02），通过后解析为结构化树并与当前库内版本按键路径计算 diff，返回：变更节点清单（键路径 + 动作 + 类型）、计数统计、task_id、apply 命令示例。
  2. diff 的动作语义：new（库中不存在）、replace（键路径相同、值或结构变化）、delete（库中存在、新文件已移除）、keep（无变化）。
  3. apply 接口必须以 preview 返回的 task_id 为入参，并校验一次性 apply token；成功后任务置 applied，生成版本快照；失败置 failed 并记录错误，不产生新版本。
  4. 同一配置同时只允许一个进行中的推送任务；冲突时提示"已有待提交任务，请先完成或取消"。

结果与状态

推送成功 → 配置列表出现新条目（或原文更新），版本数 +1；preview 阶段任何校验失败都不产生副作用。任务状态机：pending → applied | failed。

异常

文件为空、超出大小上限、token 过期/已用、task_id 非数字或与预览不一致、目标行业不存在——均返回明确中文错误，不落库。

FR-02 语法校验与错误定位P1

处理规则

  1. 推送与全文编辑保存时均执行 YAML 语法校验。
  2. 错误定位：返回行号 + 列位置 + 可读说明（例如"第 1143 行缩进层级不一致：mariadb_password 与同级键未对齐"、"重复键：clusters 下出现两次 name=jdk"）。
  3. 校验失败时：推送场景在 preview 阶段拦截；编辑场景允许用户选择"放弃保存"或"仍以原文保存为草稿（标记为非法）"。非法配置不参与 apply 与版本快照，列表中带"语法异常"标记。

样例启示：所附 deploy_config.yml 存在缩进层级不整齐、行内注释密集、个别键未加引号等写法，严格解析有风险。因此产品必须提供"严格校验 + 错误定位"，而不是静默失败或静默改写原文。

FR-03 结构化解析与注释保真P0

处理规则

  1. 解析器把 YAML 文本转换为节点树，节点类型至少覆盖：根文档、映射、列表、列表项、标量值、独立注释行、行内注释。
  2. 每个非注释节点记录键路径（如 clusters[3].cluster-variables.redis.sentinel.master），作为 diff、定位、导航的统一标识；同时记录行号范围用于前后端联动。
  3. 注释保真：独立注释行作为注释节点保留在原位置；行内注释（如 name: "docker" #node软件包）附着在所在节点上。重新导出时按节点顺序与附着关系还原，保证原文可近似无损回退。
  4. 解析失败但不致命的结构问题（如个别缩进歧义）不中断流程，进入"宽松模式"：仍保存原文，树只呈现可解析部分，并提示"部分内容未能结构化"。决策

FR-04 内容浏览：全文 + 树双视图联动P0

布局

配置详情页左侧为结构化树（可折叠，展示键路径层级与类型徽标），右侧为全文视图（语法高亮、行号）。两者联动：点击树节点，右侧全文滚动并高亮该节点对应的行区间；在全文选中某行，树自动展开并定位到对应节点。

处理规则

  1. 树节点显示：映射键名、列表项序号、标量值（超长值截断显示并可在全文查看完整值）。
  2. 支持按关键词在树中过滤节点（命中键名或值），支持在全文视图搜索并高亮所有命中。
  3. 视图仅展示，编辑入口见 FR-05。

样例参考

对 deploy_config.yml，树顶层呈现 hosts、service_mode、clusters、networking；点击 clusters[14].cluster-variables.s3.public.secretKey 时，全文定位到第 234 行并高亮该键值对。

FR-05 内容编辑P0

目的与触发

用户需要修正或调整配置内容，而不重新推送整个文件。

处理规则

  1. 全文编辑（主方式）：右侧全文视图进入编辑态，保存前执行语法校验（FR-02），成功后整树按新原文重新解析并更新节点，同时生成新版本快照。
  2. 节点级操作（辅助）：在树中对单个标量节点支持改值；对映射/列表项支持重命名键、删除节点（危险操作需确认）、新增子节点。保存后同样走"重新解析 → 更新树 → 生成版本"。
  3. 两种编辑共用同一落库通道，任何一次成功保存都产生一个版本快照；保存操作记录操作人与时间。
  4. 并发保护：采用乐观锁，保存时版本号不匹配则提示"内容已被他人修改，请刷新后重试"，不做自动合并。

异常

删除含子节点的映射/列表项需二次确认并提示影响范围（如"将删除 3 个子节点"）；编辑导致语法非法时按 FR-02 的草稿规则处理。

FR-06 版本快照、对比与回滚P0

处理规则

  1. 每次 apply 成功或编辑保存成功，自动生成版本快照（完整原文 + 时间 + 操作人）。
  2. 版本列表按时间倒序展示，支持查看任意版本的全文。
  3. 支持任意两版本全文 diff 对比：行级增删改高亮，并附"结构层面共变更 N 个节点"摘要。
  4. 回滚：选择历史版本执行"回滚"，系统以该版本原文生成一次编辑保存（即生成新版本，而非覆盖历史），保留完整审计轨迹。

FR-07 导出与回推命令P0

处理规则

  1. 任意时刻可从当前内容导出为原始 YAML 文本（下载文件或复制到剪贴板），内容与库内 content_text 一致。
  2. 界面展示"推送命令"卡片：自动生成 preview 与 apply 两段 curl 示例，含公网可达基址与一次性 token 占位符（与 Nginx 推送一致的交互）。
  3. 导出与推送必须双向一致：推送进去的原文经"解析→重新序列化"后，除规范化空白外应与源文件一致（注释、顺序、值类型不丢失）。

7. 设计决策摘要（评审要点）

  1. 通用 YAML 而非绑定样例结构：产品按树形结构管理任意 YAML，样例仅作验证载体。理由：绑定 schema 会限制复用，且"键路径 + 行号"两套定位机制已能覆盖样例的业务化诉求。
  2. 复用现有"配置文件管理"范式而非新造轮子：推送两阶段、一次性 token、行业归属、版本快照、导出回推与 Nginx 系统同构，只替换"解析器 + 树模型 + 视图"三处。建议实现时抽象公共底座，避免两套系统各自维护推送/版本/权限逻辑。
  3. 全文优先、树为辅：YAML 以文本形式被运维日常维护，与 Nginx 以块为编辑单元不同，主编辑方式是全文+语法高亮，树承担导航与定位职责。
  4. 容错解析 + 显式校验：既不能拒绝常见"缩进不齐"的工业文件，也不能静默篡改原文。用"宽松保存原文 + 严格定位提示"保证双向无损。
